# Database Schema

## Sources and Scope

The schema is defined by [`data/setup_database.sql`](../data/setup_database.sql) followed by [`data/migration_rubric.sql`](../data/migration_rubric.sql). This document describes the final structure produced by the two scripts. Only `migration_rubric.sql` is safe to re-run on a database that holds data, because `setup_database.sql` drops its tables first.

The deployed database could not be inspected, so “confirmed” below means confirmed by repository DDL; additional deployed objects or constraints may exist.

The scripts define **8 confirmed tables**, **1 view**, and **1 confirmed foreign key**. Supabase Auth is used by the application, but its managed `auth` schema is not defined by this project SQL and is not included as a project table here.

`SERIAL` columns are PostgreSQL integer columns with sequence-generated defaults. Unless stated otherwise, columns without `NOT NULL` are nullable. Defaults do not imply `NOT NULL`.

## Relationships

| Referencing column → referenced column | Cardinality | Optionality / evidence |
|---|---|---|
| `bills.promotion_id` → `promotions.id` | N:1 from bills to promotions; equivalently 1:N from promotions to bills | Optional on the bill side because `promotion_id` is nullable. Declared in `data/setup_database.sql`. |

There are no confirmed 1:1 or N:M relationships in the project SQL, and no junction tables are defined.

## RLS Policies

Row-level security is enabled on every table. `migration_rubric.sql` replaces the original administrator policies, which failed with `infinite recursion detected in policy for relation "tenant_profiles"` because they queried `tenant_profiles` from within its own policy. Administrator checks now use the `SECURITY DEFINER` function `public.is_admin()`.

| Table | Anonymous | Tenant | Administrator |
|---|---|---|---|
| `tenant_profiles` | None | Own row | All |
| `bills` | None | Read own, send slip | All |
| `maintenance_requests` | None | Own rows | All |
| `promotions` | Read active | Read active | All |
| `appointments` | None | None | All |
| `rooms` | Read | Read | All |
| `announcements` | None | Read | All |
| `messages` | Send booking requests | Own conversation | All |

Two triggers limit what tenants can change through the API. `protect_profile_fields` keeps `role`, `room_no`, and the lease fields unchanged, and `protect_bill_fields` only allows a tenant to set `status` to `checking` and attach `slip_image`.

## Design Checks

- `bills.email` and `maintenance_requests.email` are required strings, but neither references the unique `tenant_profiles.email`. The database can therefore contain orphaned billing or maintenance records if a profile is removed or an email changes. The admin billing page joins the two tables by email in JavaScript.
- `tenant_profiles.room_no` and `bills.room_no` are plain nullable text columns with no FK to a room entity. The SQL also has no uniqueness constraint on tenant room assignments or on a tenant's bill month, so the admin pages check for duplicates before saving.
